FUNDAMENTALS

1. HTTP & REST Fundamentals

Q1: What actually makes an API RESTful?
  • Resources as nouns — /orders/42, not /getOrder?id=42
  • HTTP verbs carry the action — GET/POST/PUT/PATCH/DELETE
  • Stateless — every request carries what's needed (token, params); no server-side conversation memory
  • Representations — the same resource can be JSON today, CSV tomorrow, negotiated via headers
  • Uniform status codes and cacheability

Most "REST" APIs are pragmatic REST — that's fine; be able to say which constraints you kept and why.

Q2: HTTP methods — semantics and idempotency?
Method Meaning Idempotent?
GET Read, no side effects Yes (and safe)
POST Create / non-idempotent action No
PUT Replace whole resource Yes
PATCH Partial update Not guaranteed
DELETE Remove Yes

Idempotent = same result no matter how many times it's retried — that's what makes retries and load balancers safe. It's why "submit payment" needs an idempotency key on POST.

Q3: Which status codes must an API get right?
  • 200 OK · 201 Created (+ Location header) · 204 No Content (deletes)
  • 301/308 moved · 304 Not Modified (caching)
  • 400 bad input · 401 not authenticated · 403 authenticated but not allowed · 404 not found · 409 conflict (duplicate) · 422 validation failed · 429 rate limited
  • 500 our bug · 502/503 upstream/overloaded
Q4: Why must the API layer be stateless?

If any server can answer any request, you can add servers behind a load balancer and kill unhealthy ones freely. State that must live somewhere moves out of the process: sessions → Redis or JWT, uploads → object storage, jobs → a queue. "Can I run three copies of this behind a load balancer with zero code changes?" is the test.

Q5: Rules of thumb for resource URL design?
GET  /api/products               list (filter via query: ?category=&sort=)
POST /api/products               create
GET  /api/products/:id           read one
PATCH /api/products/:id          update
GET  /api/products/:id/reviews   nested resource — one level deep max
POST /api/orders/:id/cancel      action that isn't CRUD → verb sub-resource

Plural nouns, kebab-case, no verbs in paths (except explicit action endpoints), filters and pagination in the query string.

Q6: How do you version an API?
  • URL — /api/v2/...: visible, cache-friendly, most common
  • Header — Accept: application/vnd.app.v2+json: cleaner URLs, harder to test by hand
  • Best defense is not breaking things: additive changes (new optional fields) need no version bump; reserve versions for removed/renamed fields and changed semantics
Q7: Which request/response headers earn their keep?
  • Authorization — Bearer <token>
  • Content-Type / Accept — what I'm sending / what I can read
  • Cache-Control, ETag, Last-Modified — the caching contract
  • X-Request-Id — correlate one request across services and logs
  • Retry-After — pairs with 429/503
Q8: What does HTTPS actually protect — and not?

TLS gives confidentiality (nobody reads the traffic), integrity (nobody alters it), and server authenticity (you're talking to the real host). It does not validate input, stop injection, or authenticate the user — app-layer security still applies. Terminate TLS at the proxy/load balancer; redirect HTTP → HTTPS; add HSTS.

AUTH & DATA FLOW

2. Auth, Validation & Data Flow

Q9: JWT vs server sessions — the real tradeoff?
  • Sessions — random id in a cookie, data on the server (Redis). Instant revocation, tiny cookie; needs shared session store to scale
  • JWT — signed claims live in the token itself. Stateless verification (any server, no store hit); but revocation is hard — you end up with short expiry + refresh tokens, or a denylist (which is a session store again)

Strong answer: JWTs shine for service-to-service and multi-API setups; plain sessions are simpler and safer for a single web app. Say the expiry/revocation caveat before they ask.

Q10: Where should the client store tokens?
  • localStorage — readable by any JS on the page → one XSS bug leaks it. Convenient, risky
  • httpOnly + Secure + SameSite cookie — invisible to JS (XSS can't read it), sent automatically; now consider CSRF, which SameSite=Lax/Strict plus CSRF tokens for unsafe methods handles
  • Common production pattern: access token in memory, refresh token in an httpOnly cookie
Q11: Sketch the refresh-token flow.
login  → issue access token (5–15 min) + refresh token (days, httpOnly)
request → send access token; on 401 …
refresh → POST /auth/refresh (cookie goes along) → new access token
rotate  → each refresh issues a NEW refresh token and invalidates the old
          (reuse of an old one = theft signal → kill the whole session)

Short access life bounds the damage of a leaked token; rotation makes a stolen refresh token detectable.

Q12: How do you store passwords?

Never encrypted, always hashed with a slow, salted algorithm — bcrypt (cost ~10–12) or argon2. The salt is generated per password and stored inside the hash string; identical passwords still produce different hashes, and rainbow tables die. 

const hash = await bcrypt.hash(password, 12);      // register
const ok = await bcrypt.compare(password, hash);   // login
Q13: Where does input validation belong?

At the API boundary, before any handler logic — schema validation (zod / joi / express-validator) for shape and types, then business rules deeper in. Client-side validation is UX only; the server never trusts it. Reject with 400/422 and a machine-readable field list. 

const CreateUser = z.object({
  email: z.string().email(),
  password: z.string().min(12),
  age: z.coerce.number().int().min(13).optional(),
});
// route: const data = CreateUser.parse(req.body)  → throws → error middleware
Q14: Offset vs cursor pagination — API view?
  • Offset (?page=3&limit=20) — jump to any page; slow when deep (DB scans skipped rows) and unstable when rows are inserted mid-browse
  • Cursor (?after=eyJpZCI6…) — "give me what follows this opaque marker": stable and fast at any depth; no random page jumps

Return paging metadata either way: { data, nextCursor } or { data, page, total }.

Q15: How do file uploads work at scale?

Small scale: multipart/form-data through the API (multer), store on disk or object storage. Real scale: the API only issues a pre-signed URL; the browser uploads directly to S3-style storage, then confirms — your Node process never streams gigabytes. Always cap size, whitelist MIME types, and never trust the client's filename.

Q16: What does a good error response look like?
{
  "error": {
    "code": "VALIDATION_FAILED",       // stable, machine-readable
    "message": "Email is invalid.",    // human-readable, no internals
    "fields": { "email": "invalid" },
    "requestId": "req_8fk2…"           // findable in your logs
  }
}

One shape everywhere, stable codes the frontend can switch on, no stack traces or SQL in production, and the request id that connects a user report to the exact log line.

Q17: Rate limiting — why, and which algorithm?

Protects against brute force, scraping, and one noisy client starving everyone. Algorithms: fixed window (simple, bursty at boundaries), sliding window (smooths that), token bucket (steady rate + allows bursts — the usual pick). Keep counters in Redis so limits hold across instances; answer 429 + Retry-After. Tighter buckets on /login and /refresh.

Q18: Explain CORS in one minute.

Browsers block cross-origin reads by default. CORS is the server saying "this origin may read me" via Access-Control-Allow-Origin. Non-simple requests (JSON content type, auth headers, PUT/DELETE) trigger a preflight OPTIONS asking permission first. With credentials, the allowed origin must be exact — no *. It protects browser users, not your API — curl ignores it; auth still does the real gatekeeping.

SCALING & ARCHITECTURE

3. Scaling & Architecture

Q19: Walk through the caching layers of a MERN app.
  1. Browser — Cache-Control on static assets (hashed filenames → cache forever)
  2. CDN — static files and cacheable GETs at the edge
  3. App cache (Redis) — hot query results, sessions, computed aggregates
  4. Database — indexes and its own working-set memory

The interview follow-up is always invalidation: TTLs for tolerable staleness, key-based invalidation on writes (delete product:42 when product 42 changes), and cache-aside as the default pattern — read cache → miss → read DB → fill cache.

Q20: Horizontal vs vertical scaling?

Vertical — bigger machine: zero code changes, quick win, has a ceiling and a single point of failure. Horizontal — more machines behind a load balancer: near-limitless and fault-tolerant, but demands statelessness (Q4), centralized sessions, and sticky-free design. Node specifics: one process uses one core — cluster/PM2 to use the whole box, then multiply boxes.

Q21: What does a load balancer do — and what are sticky sessions?

Spreads requests across healthy instances (round-robin / least connections), checks health, and removes dead nodes. Sticky sessions pin a user to one instance — a crutch for in-memory state that breaks the moment that instance dies; move state to Redis instead. Nginx or a cloud LB also terminates TLS and can serve static files.

Q22: Database scaling — in what order?
  1. Indexes + query fixes — 90% of "we need to scale" cases end here
  2. Caching — keep reads off the DB entirely
  3. Replica set — replicas for availability (and read-heavy offloading, accepting staleness)
  4. Sharding — split data across machines by shard key; operationally expensive, last resort
Q23: WebSockets vs SSE vs polling?
  • Polling — request every N s: simple, laggy, wasteful; fine for infrequent changes
  • SSE — one-way server→browser stream over plain HTTP: perfect for feeds, notifications, progress
  • WebSockets — full duplex: chat, games, collaborative editing. At scale, publish across instances via Redis pub/sub so a message reaches users connected to other nodes
Q24: When does a message queue enter the design?

Whenever the response shouldn't wait on the work: emails, image processing, webhooks, report generation. The API enqueues (BullMQ / RabbitMQ / SQS), answers 202, workers consume with retries and a dead-letter queue. You get spike-smoothing, failure isolation, and independent scaling of the slow parts.

Q25: Monolith or microservices for a MERN product?

Start modular monolith: one deployable, clean internal module boundaries (routes/services/models per domain). Split a service out only when something forces it — a component scaling very differently, a team boundary, a different runtime. Microservices buy independent deploys at the price of network failures, distributed data, and much heavier ops. Saying "monolith first, and here's what would make me split" reads as experience, not timidity.

Q26: What does a production MERN deployment look like?
DNS → CDN (static React build)
    → Nginx / cloud LB (TLS, gzip)
      → Node/Express × N  (PM2 or containers; stateless)
        → MongoDB replica set (managed: Atlas)
        → Redis (cache, sessions, rate limits, queues)
CI: test → build → deploy; config via env vars; logs + metrics shipped out

Key phrases: twelve-factor config, health-check endpoint, graceful shutdown (stop accepting, finish in-flight, close DB), zero-downtime rolling deploys.

DESIGN TASKS

4. Design Tasks (Whiteboard Rounds)

Task 1: Design a URL shortener.

Clarify first: scale (reads ≫ writes), custom aliases? analytics? expiry?

  • Model: { code, longUrl, ownerId, createdAt, expiresAt, clicks }, unique index on code
  • Code generation: base62-encode an auto-incrementing counter (or random 7 chars + retry on collision). 62⁷ ≈ 3.5T — plenty
  • Redirect path: GET /:code → cache lookup (Redis) → 301/302 → increment clicks async (queue, not in the hot path)
  • Scale story: redirects are cache hits; DB only on miss; shortening is the rare write
Task 2: Design real-time chat.
  • Transport: WebSockets (socket.io) with auth at connection time (token in the handshake)
  • Model: conversations + messages ({ convId, senderId, body, sentAt, readBy[] }), index on (convId, sentAt), cursor-paginate history
  • Delivery: persist first, then broadcast to the room; multiple Node instances share a Redis pub/sub adapter so sockets on other nodes get it
  • Extras when asked: typing = ephemeral events (never stored), unread counts precomputed per user, presence via heartbeat TTL keys in Redis
Task 3: Design a product listing with search, filters, pagination.
  • API: GET /products?q=&category=&minPrice=&sort=price&after=… — every filter optional, cursor pagination, whitelist sort fields
  • Mongo: compound indexes matching the hot filter+sort combos ({ category: 1, price: 1 }); text or Atlas Search index for q; facet counts via aggregation, cached
  • Frontend: filters live in the URL (shareable, back-button-safe), debounce the search box, keep previous page's data while the next loads
  • Scale story: cache popular first pages; a dedicated search engine (Elastic/Atlas Search) when relevance ranking matters
