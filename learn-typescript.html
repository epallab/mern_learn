// module 01

What TypeScript Is (and Isn't)

Types exist only at compile time

TypeScript = JavaScript + a static checker. Compilation erases every annotation — the runtime never sees them. So types can't validate API responses or user input by themselves; they document and enforce what your code believes. 

const n: number = JSON.parse('"actually a string"');
// compiles fine, lies at runtime — validation (zod) bridges this gap
"Do types exist at runtime?" — no, erased. Follow-up "so how do you trust API data?" — runtime validation at the boundary, which can also infer the static type (zod's z.infer).

tsconfig: the handful that matters

{
  "compilerOptions": {
    "strict": true,              // the whole strict family — non-negotiable
    "target": "ES2022",          // what syntax to emit
    "module": "NodeNext",        // how imports resolve
    "noUncheckedIndexedAccess": true,  // arr[i] is T | undefined — honest
    "skipLibCheck": true
  }
}

Everything else is project detail. Know what strict turns on and why you want it from day one.

What strict actually buys you

  • strictNullChecks — null/undefined stop being members of every type; the compiler forces the "what if it's missing?" conversation
  • noImplicitAny — unannotated, uninferable parameters are errors instead of silent any
  • strictFunctionTypes / strictBindCallApply — function assignments and .call are checked properly
"Is your codebase strict?" is a culture probe. The good answer: strict on new code always; legacy migrates incrementally.

// module 02

Type Basics

Inference first, annotation second

let port = 3000;            // inferred number — annotation would be noise
const app = express();      // inferred Express

// annotate where inference can't reach: parameters and public returns
function priceAfterTax(price: number, rate: number): number {
  return price * (1 + rate);
}

Let inference do local work; write types at boundaries — function signatures, module exports, API shapes.

Arrays, tuples, and readonly

const tags: string[] = [];
const pair: [lat: number, lng: number] = [48.85, 2.35];  // fixed length + roles
const frozen: readonly number[] = [1, 2, 3];
// frozen.push(4)  ✗ compile error

Tuples are how hook returns are typed — [value, setValue] — each slot with its own type.

Unions and literal types

type Status = "idle" | "loading" | "success" | "error";
let s: Status = "loading";
s = "done";        // ✗ not in the union

function move(dir: "up" | "down", by: number) {}

Unions of string literals replace enums in most modern codebases — zero runtime, autocomplete everywhere, impossible values impossible.

Model state as a union of literals and interviewers relax: it shows you type states, not just primitives.

any vs unknown vs never

  • any — opts out of checking entirely, and spreads; each one is a hole in the proof
  • unknown — "something, prove it before using": forces narrowing first. The correct type for catch errors and untyped input
  • never — "cannot happen": empty unions, functions that always throw; powers exhaustiveness checks 
catch (e: unknown) {
  if (e instanceof Error) log(e.message);   // must narrow before use
}
"Difference between any and unknown?" is the single most common TS screener. unknown = safe any.

Assertions: as, !, and satisfies

const el = document.querySelector("#app") as HTMLDivElement; // you promise
input!.focus();                       // non-null assertion — you promise again

const theme = {
  primary: "#7048b6",
  space: [0, 4, 8],
} satisfies Record<string, string | number[]>;
// checked against the shape, but keeps the NARROW inferred types

Assertions silence the checker without changing runtime — every one is a place tests can't save you. satisfies validates without widening; prefer it for config objects.

// module 03

Narrowing

The compiler tracks what it knows about a value through your control flow. Narrowing is writing code the tracker can follow.

The built-in guards

function format(v: string | number | Date) {
  if (typeof v === "string") return v.trim();     // v: string here
  if (v instanceof Date) return v.toISOString();  // v: Date here
  return v.toFixed(2);                            // only number remains
}

if ("error" in response) { /* response narrowed by property presence */ }

Discriminated unions — the pattern

Give every variant a common literal field (kind, status); switching on it narrows to the exact variant. This is how you make illegal states unrepresentable. 

type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }        // data EXISTS only on success
  | { status: "error"; error: string };

function view(s: FetchState<User[]>) {
  switch (s.status) {
    case "success": return render(s.data);   // s.data is User[] — proven
    case "error":   return show(s.error);
    default:        return spinner();
  }
}
"Type a data-fetching state" is the canonical TS interview exercise — this shape, verbatim. It also kills the data?: T; error?: string anti-pattern where both can exist at once.

Custom guards: type predicates

function isUser(v: unknown): v is User {
  return !!v && typeof v === "object" && "email" in v;
}
const users = list.filter(isUser);   // unknown[] → User[]

The v is User return type teaches the compiler your runtime check. filter + predicate is the everyday use.

Exhaustiveness with never

switch (shape.kind) {
  case "circle": return Math.PI * shape.r ** 2;
  case "square": return shape.size ** 2;
  default: {
    const unreachable: never = shape;  // add "triangle" to the union →
    return unreachable;                // this line turns red. Free regression test.
  }
}
Mentioning the never-default trick unprompted is a strong senior signal — it makes the compiler enforce that new variants get handled.

// module 04

Object Types

interface vs type — the honest answer

For object shapes they're interchangeable. Real differences: type can alias anything (unions, tuples, mapped types); interface supports declaration merging (re-opening — how Express's Request gets extended) and reads slightly better in errors. Pick one per codebase and be consistent — the debate itself is the interview trap. 

interface User { id: string; email: string; }
type Result = User | null;            // only type can do this

Optional and readonly members

interface Todo {
  readonly id: string;      // set once, never reassigned
  title: string;
  dueAt?: Date;             // Date | undefined — callers must handle it
}

? means "may be absent" — with exactOptionalPropertyTypes that's different from "may be explicitly undefined". readonly is compile-time only; it doesn't freeze the runtime object.

Index signatures and Record

interface Scores { [userId: string]: number }
type Scores2 = Record<string, number>;          // same thing, tidier

type Ramp = Record<"beginner" | "advanced", string>;  // exhaustive keys:
// missing "advanced" → compile error

Record with a literal-union key is quietly powerful: the compiler guarantees every key is present.

Composing: extends and intersections

interface Timestamped { createdAt: Date; updatedAt: Date; }
interface Post extends Timestamped { title: string; }

type Draft = Post & { status: "draft" };   // intersection — type's version

Conflicting members: extends errors loudly (good); intersections silently produce never (confusing). Another point for interface when modeling plain shapes.

Structural typing — duck typing, checked

Compatibility is by shape, not by name: any object with the right members satisfies the type. Fresh object literals get extra strictness (excess property checks) — passing a literal with an unknown key errors, while the same object via a variable passes. 

interface Point { x: number; y: number }
const p3d = { x: 1, y: 2, z: 3 };
const p: Point = p3d;              // fine — has at least x and y
const q: Point = { x: 1, y: 2, z: 3 };  // ✗ excess property on a literal
"Why does it error inline but not via a variable?" — excess property checking on fresh literals. Rarely known; easy to shine.

// module 05

Functions & Generics

Typing functions

type Comparator<T> = (a: T, b: T) => number;      // a function TYPE

const byPrice: Comparator<Product> = (a, b) => a.price - b.price;
// params infer from the alias — no re-annotating

function log(level: "info" | "error", msg: string, meta?: object): void {}

Generics: types as parameters

A generic function promises a relationship: "whatever type comes in, that's what goes out." Without it you'd choose between duplicating code and losing the type to any. 

function first<T>(arr: T[]): T | undefined {
  return arr[0];
}
first([1, 2, 3]);        // T inferred as number
first(users);            // T inferred as User — no call-site annotation
"Write a typed identity/first/pluck function" is the standard can-you-generics test. Let inference do the call sites.

Constraints: extends

function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((i) => i[key]);
}
pluck(users, "email");   // string[] — and "emial" is a compile error

K extends keyof T ties the second argument to the first's real keys. This one signature is the most-asked generics exercise in interviews.

Generics in the wild: typed API client

async function api<T>(path: string): Promise<T> {
  const res = await fetch(path);
  if (!res.ok) throw new HttpError(res.status);
  return res.json() as Promise<T>;    // the honest cast at the boundary
}
const todos = await api<Todo[]>("/api/todos");

The assertion is the trust boundary — pair it with runtime validation (zod) when the API isn't yours.

Overloads and default type params — know they exist

function get(key: "port"): number;          // overloads: precise per-input
function get(key: "host"): string;          // return types
function get(key: string): unknown { return config[key]; }

type ApiResponse<T = unknown> = { data: T; requestId: string };

Overloads model "return type depends on the argument"; usually a union or generic does the job with less ceremony — say that.

// module 06

Utility & Derived Types

One source-of-truth type, everything else computed from it — the skill that separates TS users from TS writers.

The everyday utilities

interface User { id: string; email: string; name: string; role: Role }

type UserPatch  = Partial<User>;               // all optional — update DTOs
type PublicUser = Omit<User, "email">;         // drop fields
type Credentials = Pick<User, "id" | "role">;  // keep fields
type UserMap    = Record<string, User>;
type Frozen     = Readonly<User>;
"How would you type an update payload?" — Partial<Omit<User, "id">>. Composing two utilities in one breath is exactly the expected register.

Extracting from functions: ReturnType, Parameters, Awaited

function buildStore() { return { todos: [] as Todo[], filter: "all" }; }
type Store = ReturnType<typeof buildStore>;     // type follows the code

type Row = Awaited<ReturnType<typeof fetchRows>>[number];
//         unwrap Promise ─┘        └─ element type of the array

Deriving types from implementations means refactors update the types for free.

keyof and typeof

const COLORS = { str: "#22834f", fn: "#2e66c7", kw: "#7048b6" } as const;
type Token = keyof typeof COLORS;      // "str" | "fn" | "kw"
type Hex   = (typeof COLORS)[Token];   // the value union

function color(t: Token) { return COLORS[t]; }  // impossible to typo

as const keeps literals narrow; keyof/typeof turn a runtime constant into its own type. The end of hand-maintained string unions.

Mapped and conditional types — read them, sparingly write them

type Nullable<T> = { [K in keyof T]: T[K] | null };   // mapped: transform each key

type UnwrapArray<T> = T extends (infer U)[] ? U : T;  // conditional + infer
UnwrapArray<Todo[]>;   // Todo

This is the machinery the built-in utilities are made of. In application code, reach for the built-ins first; write custom ones when a real pattern repeats.

Template literal types — a taste

type Route = `/api/${string}`;
const ok: Route = "/api/users";     // ✓
const no: Route = "/users";         // ✗

type EventName = `on${Capitalize<"click" | "focus">}`;  // "onClick" | "onFocus"

Types that understand string structure — how libraries type route params and event maps. Recognize it; don't build a type-level parser in an interview.

// module 07

Classes & Enums

Class typing: modifiers and implements

interface Repo<T> { find(id: string): Promise<T | null>; }

class UserRepo implements Repo<User> {
  constructor(private db: Db, readonly name = "users") {}
  //          └ parameter property: declares + assigns in one stroke
  async find(id: string) { return this.db.collection(this.name).findOne({ id }); }
}

private/protected are compile-time (JS #fields are the runtime-real version); implements checks the shape without inheriting anything.

Enums vs as const — the modern verdict

enum Role { Admin = "admin", User = "user" }     // generates runtime code

const ROLES = ["admin", "user"] as const;        // the lighter idiom
type Role2 = (typeof ROLES)[number];             // "admin" | "user"
// runtime list for validation + static union, no emitted enum object
"Do you use enums?" — expected answer: literal unions + as const for the runtime list; string enums only when a team already standardized on them.

Abstract classes — when a base contract needs shared code

abstract class Job {
  abstract run(): Promise<void>;          // subclasses must implement
  async execute() {                       // shared wrapper: retry/log once
    let lastErr;
    for (let i = 0; i < 3; i++) {
      try { return await this.run(); } catch (e) { lastErr = e; }
    }
    throw lastErr;
  }
}

Interface = contract only; abstract class = contract + shared implementation. If there's no shared code, use the interface.

TypeScript in React

Props: the everyday shape

interface ButtonProps {
  variant?: "primary" | "ghost";
  disabled?: boolean;
  onClick?: () => void;
  children: React.ReactNode;      // anything renderable
}

function Button({ variant = "primary", ...rest }: ButtonProps) { … }

React.FC is optional and mostly avoided now — a plain function with a typed props parameter infers the rest.

Typing hooks

const [user, setUser] = useState<User | null>(null);  // annotate when it starts empty
const [count, setCount] = useState(0);                // inferred — leave it

const inputRef = useRef<HTMLInputElement>(null);      // DOM ref
const timerRef = useRef<ReturnType<typeof setTimeout>>(undefined); // mutable box

const [state, dispatch] = useReducer(reducer, initial);
// type the ACTION as a discriminated union → dispatch is fully checked
The useState<User | null>(null) line is the most-asked React+TS question: empty initial state needs the union spelled out.

Event types

function onChange(e: React.ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value);            // target is typed — .value exists
}
function onSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
}
// inline handlers usually infer these — spell them out for extracted ones

Generic components and hooks

function useFetch<T>(url: string) {
  const [state, setState] = useState<FetchState<T>>({ status: "idle" });
  // …
  return state;    // FetchState<T> — the discriminated union from module 03
}

interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}
function List<T>({ items, renderItem }: ListProps<T>) { … }

The generic flows from the data to the render callback — item is fully typed inside renderItem at every call site.

Extending native element props

interface FieldProps extends React.ComponentPropsWithoutRef<"input"> {
  label: string;
  error?: string;
}
function Field({ label, error, ...inputProps }: FieldProps) {
  return (
    <label>
      {label}
      <input aria-invalid={!!error} {...inputProps} />
    </label>
  );
}

Your wrapper accepts everything a real input does — placeholder, onBlur, name — without re-declaring any of it.

// module 09

TypeScript in Node & Migration

Typing Express handlers

import type { Request, Response, NextFunction } from "express";

// Request<Params, ResBody, ReqBody, Query>
app.post(
  "/users/:id",
  (req: Request<{ id: string }, unknown, UpdateUserDto>, res: Response) => {
    req.params.id;    // string — typed
    req.body.email;   // from UpdateUserDto
  }
);

The generic slots on Request are the interview detail: params, response body, request body, query — in that order.

Extending Request (declaration merging, for real)

// types/express.d.ts
declare global {
  namespace Express {
    interface Request {
      user?: { id: string; role: "admin" | "user" };
    }
  }
}
// auth middleware sets req.user; every handler sees it typed
"How does req.user get its type?" — declaration merging on the Express namespace. Knowing the mechanism's name matters.

Typed config: validate env once

const Env = z.object({
  PORT: z.coerce.number().default(3000),
  MONGO_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
});
export const env = Env.parse(process.env);   // crashes at BOOT, not at 3am
// typeof env is inferred — z.infer bridges runtime → static

Sharing types across the stack

The MERN payoff: one shared/types.ts (or workspace package) exporting the API DTOs; server handlers and React fetch hooks import the same definitions. Rename a field → both sides turn red before anything deploys. Zod schemas as the source of truth give you the runtime validators and the types from one declaration.

Migrating a JS codebase

  1. allowJs: true — TS and JS coexist; nothing breaks
  2. Rename leaf files first (utils, constants) — fewest dependents
  3. strict on for new files; ratchet flags up per folder
  4. Kill each any deliberately — every one is a TODO
  5. Types at the boundaries first: API DTOs, then inward
Migration strategy is a favorite senior question — the winning shape is "incremental, boundaries-first, strictness ratcheted, no big-bang rewrite".
