BEGINNER LEVEL

1. Complexity & Big-O

Q1: What is Big-O, and why do interviewers care?

Big-O describes how an algorithm's cost grows with input size, ignoring hardware and constants. Interviewers care because it's the shared language for comparing approaches — "can you do better than O(n²)?" is really the whole game of the coding round.

Q2: Rank the common complexities with an example each
  • O(1) — array index, Map.get
  • O(log n) — binary search
  • O(n) — one pass: includes, Kadane
  • O(n log n) — good sorts: merge sort, Timsort
  • O(n²) — nested loops: naive two-sum
  • O(2^n) — all subsets, naive fibonacci
  • O(n!) — all permutations
Q3: Why do we drop constants and lower-order terms?

Because Big-O describes the shape of growth, not the running time. For large n, the n² term in 3n² + 50n dwarfs everything else — so it's O(n²). Worth adding out loud: constants still matter in practice, which is why a hashmap "O(1)" can lose to a small array scan.

Q4: Best, average, worst case — which one is Big-O?

By convention interviews mean worst case unless stated. The classic example is quicksort: O(n log n) average but O(n²) worst (already-sorted input with a bad pivot). Saying "average O(n log n), worst O(n²), and here's how the pivot fixes it" is the complete answer.

Q5: What's the intuition for O(log n)?

Each step cuts the remaining work by a constant factor (usually half). Doubling the input adds one step instead of doubling the steps — a million elements is only ~20 halvings. If your loop does i = i * 2 or discards half the search space, think log.

Q6: Big-O of the JS array operations you use daily?
Operation Complexity
arr[i], push, pop O(1) (push amortized)
shift, unshift, splice O(n) — everything after the index moves
includes, indexOf, find O(n) — linear scan
sort O(n log n)

The one that fails people: using shift() to build a queue makes the loop O(n²). Use an index pointer instead.

Q7: What is amortized complexity?

The average cost per operation over a sequence, even if single operations are occasionally expensive. push is the canonical case: when the backing storage fills, the engine reallocates and copies (O(n) that one time), but doubling capacity makes the copies rare enough that the average push stays O(1).

Q8: Time vs space tradeoff — give a concrete example

Two-sum: the nested-loop version is O(n²) time, O(1) space. Add a hashmap of seen values and it becomes O(n) time, O(n) space. Most interview "optimize this" moments are exactly this trade — say the trade, not just the answer.

Q9: Two nested loops vs two sequential loops?
for (const a of list)          // O(n + m): sequential — adds
for (const b of other) ...

for (const a of list)          // O(n × m): nested — multiplies
  for (const b of other) ...

Sequential passes add, nested loops multiply. Three passes over the same array is still O(n) — a point worth making when you write the two-pass solution.

Q10: Building a string with += in a loop — complexity?

The safe interview answer: strings are immutable, each += copies what came before, so the loop totals O(n²). Collect parts in an array and join("") for O(n). (Modern engines mitigate with internal rope structures — mention it, then give the safe answer anyway.)

DATA STRUCTURES

2. Data Structures

Q11: Array vs linked list — the real tradeoffs?
Array Linked list
Access by index O(1) O(n)
Insert/delete at front O(n) O(1)
Memory contiguous, cache-friendly scattered nodes + pointers

In JS you almost always use arrays — engines optimize them heavily and cache locality beats pointer chasing. Linked lists show up as interview material and inside real structures (LRU, React fiber), not as everyday collections.

Q12: Stack vs queue — and how do you build each in JS?

Stack is LIFO — push/pop on an array, both O(1). Queue is FIFO — but shift() is O(n), so a clean queue uses an index pointer or two stacks: 

const queue = [];
let head = 0;
queue.push(x);                 // enqueue
const item = queue[head++];    // dequeue, O(1)

Uses to name: call stack, undo history (stacks); BFS, task scheduling, rate limiting (queues).

Q13: How does a hashmap work under the hood?

Hash the key to a bucket index; store the entry there. Two keys can land in the same bucket — a collision — resolved by chaining (a list per bucket) or open addressing (probe for the next free slot). Lookups are O(1) average; a bad hash function degrades toward O(n). When the load factor grows, the table resizes and rehashes.

Q14: Map vs Object vs WeakMap — when each?
  • Map — any key type, remembers insertion order, size for free, no prototype pollution. Default for lookups keyed at runtime.
  • Object — string/symbol keys only, inherits from Object.prototype (so "constructor" in obj is true!). Right for fixed, record-like shapes.
  • WeakMap — object keys held weakly: when the key is garbage-collected the entry goes too. Right for attaching metadata to DOM nodes without leaking them.
Q15: What is a Set good for?

O(1) average membership tests and deduplication — [...new Set(arr)] is the idiomatic dedupe. Any time your solution says "have I seen this before?", the answer is a Set, and it turns an O(n²) containment loop into O(n).

Q16: Binary tree vs binary search tree?

A binary tree just limits children to two. A BST adds the ordering rule: left subtree < node < right subtree — which makes search O(h). The follow-up they want: h is log n only if the tree is balanced; insert sorted data naively and the BST degenerates into a linked list, O(n). That's why AVL/red-black trees exist (name them, don't implement them).

Q17: What's a heap, and when would a frontend dev meet one?

A binary heap is a complete tree (stored flat in an array) where each parent beats its children — giving O(1) peek at the min/max and O(log n) insert/extract. It backs priority queues: "top k frequent" problems, merging sorted streams, schedulers. In the browser world: task prioritization — React's scheduler literally uses a min-heap of tasks.

Q18: Graphs — adjacency list vs adjacency matrix?
// adjacency list — O(V + E) space, the default
const graph = { a: ["b", "c"], b: ["d"], c: [], d: [] };

// matrix — O(V²) space, O(1) edge lookup
//   worth it only for dense graphs

Real graphs (social edges, route maps, import trees) are sparse, so the list wins almost always. Say "list, because E ≪ V²" and move on.

Q19: What is a trie?

A prefix tree: one node per character, shared prefixes shared once. Lookup and insert are O(word length), independent of how many words are stored. The frontend-flavored answer: autocomplete — type "re", walk two nodes, and every completion lives in that subtree.

Q20: What structure backs an LRU cache, and why?

The classic answer is hashmap + doubly linked list: the map gives O(1) lookup, the list gives O(1) move-to-front and evict-from-back. The JS answer: Map alone works because it preserves insertion order — delete + re-set refreshes recency, and the first key is always the oldest. Give both; typing it is Practice P40.

Q21: What is a deque?

A double-ended queue — O(1) push/pop at both ends. The interview cameo is sliding window maximum: keep a deque of candidate indices, evict from the back anything smaller than the new element, evict from the front anything that left the window. Also a fine word to say when asked how browser history could support both back and forward.

Q22: Is the DOM a tree or a graph?

A tree: every node has exactly one parent, no cycles — which is why DOM problems are tree problems (walk it, measure depth, find ancestors). Two sharp follow-ups: parentNode pointers make it navigable in both directions, and React's fiber tree threads child / sibling / return pointers through it so traversal can pause and resume — a linked list woven through a tree.

ALGORITHMS

3. Algorithms

Q23: BFS vs DFS — mechanics, memory, when each wins
  • BFS — a queue, explores level by level. Memory: O(widest level). Wins: shortest path (unweighted), "nearest X", level-order UI questions.
  • DFS — a stack or recursion, dives deep first. Memory: O(depth). Wins: cycle detection, topological sort, exhaustive search/backtracking, "does a path exist".

Frontend framing that lands well: DOM walks are usually DFS (document order); "find the closest matching element outward" is BFS thinking.

Q24: Why does BFS find shortest paths in unweighted graphs?

Because it visits nodes in order of distance: everything at distance d is dequeued before anything at d+1. So the first time you reach a node, no shorter route exists. That justification — not just "use BFS" — is what the question is testing. (Weighted edges break the guarantee; that's Dijkstra, which you should name, not derive.)

Q25: Binary search — preconditions and the classic traps
function bsearch(arr, target) {
  let lo = 0;
  let hi = arr.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

Precondition: the array is sorted (or the predicate is monotonic — "first version that fails" is binary search too). The traps: lo <= hi not <, and moving mid ± 1 — get either wrong and it loops forever.

Q26: Which sort does JavaScript use? Is it stable?

V8 uses Timsort (merge sort + insertion sort hybrid), and the spec requires sort to be stable since ES2019 — equal elements keep their order, which is why sorting a user table by one column doesn't scramble the previous column's order. The gotcha to volunteer: 

[1, 10, 2].sort();            // [1, 10, 2] — compares as strings!
[1, 10, 2].sort((a, b) => a - b);  // [1, 2, 10]
Q27: Merge sort vs quicksort — compare honestly
Merge sort Quicksort
Worst case O(n log n) guaranteed O(n²) (bad pivots)
Extra space O(n) O(log n) — in place
Stable yes typically no

Quicksort is usually faster in practice (cache-friendly, in place); merge sort gives guarantees and stability. Timsort exists because real data is often partially sorted — it exploits existing runs.

Q28: Recursion — base case, call stack, and JS's limits

Every recursive solution needs a base case that terminates and a step that shrinks the problem. Each call pushes a frame onto the call stack — recurse ~10,000+ deep in JS and you get RangeError: Maximum call stack size exceeded. The senior detail: proper tail-call optimization is in the spec but only Safari ships it, so in practice you convert deep recursion to a loop with an explicit stack.

Q29: Memoization vs tabulation?
  • Memoization — top-down: recurse naturally, cache each result the first time. Easy to add to an existing solution (memoize(fn) is Practice P28).
  • Tabulation — bottom-up: fill a table from the base cases with a loop. No stack risk, often reducible to two variables — climbing stairs (P45) is the canonical example.
Q30: Greedy vs dynamic programming — how do you tell?

Both build answers from subproblems. Greedy commits to the locally best choice and never looks back — valid only when local optimum provably leads to global (interval scheduling, best time to buy stock). DP is for overlapping subproblems where choices interact (house robber: taking this element constrains the next). In an interview, try greedy, look for a counterexample; if you find one, it's DP.

Q31: When do two pointers or a sliding window apply?

Both need sequential structure you never have to re-scan: two pointers wants sorted input or an in-place partition ("move zeroes"); a sliding window wants a contiguous-range question — "longest/shortest substring/subarray with property X" — where the property is monotonic: growing the window can only make it worse, shrinking can only help. Negative numbers break that monotonicity, which is why "subarray sum = k" needs prefix sums instead (Practice P43).

Q32: What is topological sort, and where does frontend tooling use it?

An ordering of a directed acyclic graph where every edge points forward — "dependencies first". Kahn's algorithm: repeatedly take a node with in-degree 0, remove its edges. If you can't empty the graph, there's a cycle. This is exactly how bundlers order module imports, how npm resolves install order, and how build systems schedule tasks — say one of those and the interviewer relaxes.

THE FRONTEND ANGLE

4. DSA in the Browser

Q33: Why do frameworks need keys on list items?

True minimal tree diffing is O(n³) — hopeless for real UIs. React's heuristic diff is O(n): compare level by level, assume different element types mean different subtrees, and use keys to match list children across renders. Without stable keys the matcher falls back to index, so inserting at the top makes every row "change" — state resets, inputs jump. Index-as-key is the same bug with extra steps.

Q34: Describe the event loop in data-structure terms

A call stack (frames), a task queue (timers, I/O, clicks), and a microtask queue (promise callbacks). When the stack empties: drain all microtasks, then take one task, repeat. That drain-fully rule is why a chain of resolved promises runs before a 0ms timeout — and why a microtask loop can starve rendering.

Q35: Browser history — which data structure?

Model it as two stacks (back and forward: navigating pushes to back, going back pops one and pushes to forward) or one list with an index. The detail that shows depth: a fresh navigation clears the forward stack — that's why "forward" disappears after you branch off. Same structure powers undo/redo in every editor.

Q36: Debounce and throttle — what problem do they solve, formally?

Rate control over an event stream. Debounce answers "run once after the burst ends" (search-as-you-type); throttle answers "at most once per interval" (scroll handlers). Formally: debounce is a trailing-edge timer reset on every event; throttle is a time-bucketed sampler. Being able to say when each is wrong (debounced scroll feels dead; throttled search sends stale queries) is the senior half of the answer. Typing them is Practice P25–P26.

Q37: What is structural sharing in immutable updates?

When you "copy" state immutably, unchanged branches are reused, not cloned: 

const next = { ...state, user: { ...state.user, name: "Ada" } };
// next.posts === state.posts — same reference, shared structure

That's why immutable updates are cheap (O(changed path), not O(state)) and why React.memo and reducers work off reference equality. It's also why spread is shallow — you copy exactly the path you change, nothing more.

Q38: How would you detect a cycle in a dependency graph?

DFS with three colors: white (unvisited), gray (in the current path), black (done). Reaching a gray node means you've looped back into your own path — a cycle. This is precisely how bundlers emit "circular dependency" warnings, and the follow-up to Q32: topological sort fails exactly when this DFS finds gray.
