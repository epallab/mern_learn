HTML & SEMANTICS

1. HTML, Semantics & Accessibility

Q1: Why does semantic HTML matter?

Elements that say what they are — <nav>, <button>, <article> — give you three things divs don't: accessibility (screen readers get landmarks and roles free), SEO (crawlers understand structure), and built-in behavior (buttons are focusable, keyboard operable, and clickable by default). A <div onClick> re-implements all of that badly.

Q2: header vs section vs article vs aside — when each?
  • header/footer — intro/outro of the page or of any section
  • nav — major navigation blocks only
  • main — the unique content, once per page
  • article — self-contained, redistributable (a post, a card, a comment)
  • section — a thematic grouping that deserves a heading
  • aside — tangential content (sidebar, pull quote)

Test: could it stand alone in a feed? → article. Needs a heading? → section. Neither? → div is fine.

Q3: What makes a form accessible?
  • Every input gets a real <label for="id"> — placeholder text is not a label (it vanishes on type)
  • Group radios/checkboxes in <fieldset>+<legend>
  • Errors: tie the message to the field with aria-describedby and set aria-invalid
  • Right type= (email, tel) and autocomplete= attributes
  • Submit works with Enter; focus moves to the first error
Q4: Rules for alt text?

Describe the function, not the pixels: a logo linking home is alt="Acme home". Decorative images get alt="" (empty, not missing) so screen readers skip them. Never start with "image of" — it's announced anyway. Complex charts get a short alt plus a longer text alternative nearby.

Q5: script defer vs async vs plain?
  • plain — blocks parsing while it downloads and runs
  • async — downloads in parallel, runs the moment it arrives (any order) — analytics, ads
  • defer — downloads in parallel, runs after parsing, in document order — the default choice for app code

type="module" scripts defer by default.

Q6: What does the viewport meta tag do?
<meta name="viewport" content="width=device-width, initial-scale=1" />

Without it, mobile browsers render a ~980px virtual page and zoom out — your media queries never fire. This line makes the layout viewport match the device width so responsive CSS works. Don't add user-scalable=no — blocking zoom is an accessibility failure.

Q7: What are data-* attributes for?

Attaching app data to markup without inventing invalid attributes: data-user-id="42" → el.dataset.userId. Good for delegation targets, test hooks (data-testid), and CSS hooks ([data-state="open"]). Not a database — anything big or sensitive belongs in JS state.

Q8: Which SEO levers does the developer own?
  • Unique <title> and meta description per page
  • One h1, a logical heading outline, semantic landmarks
  • Canonical URLs; Open Graph tags for sharing
  • Performance (Core Web Vitals rank) and mobile rendering
  • For SPAs: server-side rendering or prerendering so crawlers see content, not an empty root div
CSS CORE

2. CSS Core Mechanics

Q9: How is specificity calculated?

Three-column score (a, b, c): a = id selectors, b = classes/attributes/pseudo-classes, c = elements/pseudo-elements. Compare column by column; later rules win ties. Inline styles outrank all selectors; !important outranks inline. 

#nav .item a      → (1, 1, 1)
.nav .item.active → (0, 3, 0)   loses to the id despite more classes
:where(.x)        → (0, 0, 0)   :where zeroes its contents — great for resets
a:hover           → (0, 1, 1)
Q10: Box model — and why set box-sizing: border-box?

Every box = content + padding + border + margin. Default (content-box): width means content only, so padding/border grow the box past your number. border-box makes width mean "the visible box" — padding and border squeeze inward. Every sane codebase starts with: 

*, *::before, *::after { box-sizing: border-box; }
Q11: display: none vs visibility: hidden vs opacity: 0?
Takes space Clickable In a11y tree
display: none No No No
visibility: hidden Yes No No
opacity: 0 Yes Yes Yes

opacity is animatable and compositor-cheap; the other two are not animatable.

Q12: The position values — and what anchors absolute?
  • static — default flow; top/left ignored
  • relative — nudged from its own spot; original space kept; becomes an anchor
  • absolute — out of flow, positioned against the nearest positioned ancestor (else the initial containing block) — forgetting position: relative on the parent is the classic bug
  • fixed — pinned to the viewport (unless an ancestor has transform/filter — that becomes the containing block; gotcha)
  • sticky — relative until its scroll threshold, then pinned within its parent
Q13: px vs em vs rem vs viewport units — when each?
  • rem — type scale and spacing; respects user font-size settings
  • em — relative to current font size: padding that scales with the text it wraps
  • px — hairlines, borders, shadows — things that shouldn't scale
  • vw/vh, % — layout proportions; dvh for mobile browser chrome
  • clamp(min, fluid, max) — fluid type without media queries
Q14: Which properties inherit — and how do inherit/initial/unset work?

Text-ish properties inherit (color, font-*, line-height, text-align, visibility); box-ish ones don't (margin, padding, border, width, background). Keywords: inherit forces the parent's value, initial the spec default, unset = inherit if inheritable else initial, revert = back to browser stylesheet.

Q15: Pseudo-class vs pseudo-element?

Pseudo-class (:) — a state of an existing element: :hover, :focus-visible, :nth-child, :not(), :has(). Pseudo-element (::) — a generated part: ::before/::after (need content), ::placeholder, ::selection. :has() is the newsworthy one — "a parent selector": label:has(input:invalid).

Q16: CSS custom properties — why better than Sass variables?

They live at runtime in the cascade: themable per scope ([data-theme="dark"] { --bg: … }), changeable from JS, readable in any rule via var(--bg, fallback). Sass variables compile away — one theme, fixed forever. This app's theme toggle is exactly this pattern.

Q17: Why does a huge z-index sometimes do nothing?

z-index only competes within the same stacking context. A new context is created by a positioned element with z-index, plus opacity < 1, transform, filter, fixed/sticky, and others. If your dropdown's parent creates a context at z-index 1, nothing inside can escape above a sibling context at 2 — fix the parents' ordering, or portal the dropdown out (what React portals are for).

Q18: Your go-to centering techniques?
/* the default answer */
.parent { display: flex; justify-content: center; align-items: center; }

/* one-liner grid */
.parent { display: grid; place-items: center; }

/* overlay / unknown size */
.child { position: absolute; inset: 0; margin: auto; width: fit-content; height: fit-content; }

/* just horizontal, block element */
.child { margin-inline: auto; max-width: 60ch; }
LAYOUT SYSTEMS

3. Flexbox, Grid & Responsive

Q19: Flexbox mental model?

One dimension at a time. The container sets direction (flex-direction), distribution along the main axis (justify-content), alignment on the cross axis (align-items), and wrapping. Children negotiate size via flex-grow / flex-shrink / flex-basis. Reach for it for toolbars, nav rows, card innards — anything that is a line of things.

Q20: What does flex: 1 actually mean?
flex: 1        →  flex: 1 1 0%     (grow 1, shrink 1, basis 0)
flex: auto     →  flex: 1 1 auto   (starts from content size)
flex: none     →  flex: 0 0 auto   (rigid)

With basis 0, spare space is shared purely by grow ratios — three flex: 1 children become exact thirds regardless of content. With basis auto, bigger content keeps a bigger share.

Q21: When Grid over Flexbox?

Grid is two-dimensional and container-driven: the parent defines tracks and children snap into them — page shells, dashboards, card grids, anything where rows and columns must agree. Flexbox is content-driven and one-dimensional. They compose: grid for the layout, flex inside each cell. 

.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 1rem;   /* the whole responsive card grid, no media queries */
}
Q22: Describe a mobile-first responsive strategy.
  • Base styles = smallest screen; min-width queries layer complexity upward
  • Breakpoints where the content breaks, not at device names
  • Fluid foundations first: clamp() type, auto-fit/minmax grids, max-width measures
  • Media queries become the exception, not the system
Q23: Media queries vs container queries?

Media queries ask about the viewport; container queries (@container) ask about the component's own box — so a card can switch layout based on the column it landed in, not the screen. Mark the parent with container-type: inline-size. This is the modern answer for reusable component libraries.

Q24: Responsive images — srcset vs picture?
<!-- same image, resolution switching: browser picks -->
<img srcset="hero-480.jpg 480w, hero-1200.jpg 1200w"
     sizes="(max-width: 600px) 100vw, 600px" src="hero-1200.jpg" alt="…" />

<!-- different crops / formats: you decide -->
<picture>
  <source type="image/avif" srcset="hero.avif" />
  <source media="(max-width: 600px)" srcset="hero-square.jpg" />
  <img src="hero.jpg" alt="…" />
</picture>

Plus loading="lazy" below the fold and explicit width/height to prevent layout shift.

Q25: Page scrolls sideways on mobile — how do you debug?

Something is wider than the viewport: unwrapped long strings, fixed widths, 100vw + padding (100vw ignores the scrollbar), negative margins, or an unconstrained flex/grid child. Find it with devtools by deleting halves, or outline everything: * { outline: 1px solid red }. Fixes: max-width: 100% on media, overflow-wrap: break-word, minmax(0, 1fr) instead of bare 1fr.

Q26: The flexbox overflow gotcha — min-width: auto?

Flex (and grid) children default to min-width: auto — they refuse to shrink below their content, so one long unbreakable string blows the layout open. Fix on the child that should give way: min-width: 0 (or overflow: hidden), then ellipsis works too: 

.row { display: flex; }
.row .title { min-width: 0; white-space: nowrap;
              overflow: hidden; text-overflow: ellipsis; }
RENDERING & PERFORMANCE

4. Rendering Pipeline & Performance

Q27: Walk the critical rendering path.

HTML → DOM; CSS → CSSOM (CSS is render-blocking); DOM+CSSOM → render tree (visible nodes) → layout (geometry) → paint (pixels into layers) → composite (GPU stacks layers). Speed it up: minimal critical CSS, defer JS, preload key assets, don't make the browser redo layout constantly.

Q28: Reflow vs repaint — and what's cheap to animate?

Reflow (layout) — geometry changed (width, top, font-size, DOM insertion); expensive, can cascade to the whole tree. Repaint — looks changed, geometry didn't (color, shadow). Cheapest: transform and opacity — compositor only, no layout, no paint. So animate position with transform: translate…, never top/left. Also: batch DOM reads then writes — interleaving them forces synchronous layout.

Q29: How do you keep an animation at 60fps?
  • Animate transform/opacity only; promote with will-change sparingly
  • Prefer CSS transitions or the Web Animations API over per-frame JS style writes
  • Per-frame JS belongs in requestAnimationFrame
  • Isolate heavy regions with contain: content
  • And respect prefers-reduced-motion — wrap non-essential motion in the media query
Q30: FOUT vs FOIT — how do you load web fonts?

FOIT — text invisible until the font arrives (worst). FOUT — fallback shows, then swaps. font-display: swap chooses FOUT deliberately; pair with preconnect to the font host, subset weights you actually use, and a metric-compatible fallback stack to shrink the swap jump.

Q31: Why CSS naming conventions (BEM) — and the modern alternatives?

CSS is global; conventions make collisions and specificity wars impossible by construction. BEM: .card__title--featured = block, element, modifier — flat specificity (0,1,0) everywhere. Alternatives that solve the same problem: CSS Modules (scoped by build), utility-first (Tailwind), @layer for cascade ordering. Interviewers want to hear "flat specificity, predictable ownership", not a religion.

Q32: How do you honor user preferences in CSS?
@media (prefers-color-scheme: dark) { :root { --bg: #16181d; } }
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}

Plus :focus-visible for keyboard users, real focus rings (never outline: none without a replacement), and WCAG contrast (4.5:1 body text). These questions increasingly decide frontend loops.
